How this works

These are scripted messages over real connections, not an animation. “Confirmed” means the server acknowledged the send, not that another user read it. Both sides use the same messages and sending rate.

The usual stack has 8 web workers, a KV cache, a message broker and a task-queue worker. Its fault runs in a web worker. PyBEAM runs the crash in an isolated child process; CPU work and exceptions use separate worker tasks. The configurations have different failure boundaries by design. This is not a throughput comparison.

Each test waits 4 s, injects the same fault on both sides concurrently, watches the other rooms for 10 s, then allows 5 s for recovery. The displayed user switches to an actually affected user, matched across both sides. Connections retry without replay. “Unconfirmed” means a pending send was discarded at disconnect; it might have reached the server.

Worker assignment and this machine affect the result. Zero disconnects does not mean zero latency impact. A lost fault request alone does not prove a process died. Keep this demo local.
