How this works

Rooms group chat messages, not server processes. Users in different rooms can share one web worker. If that worker dies, all of its connections close, regardless of room.

The request names Room 1 on both stacks and calls os.abort(), like a native extension crashing. This kills a process; an ordinary Python exception does not. The usual stack runs it in one of 8 web workers. PyBEAM sends this crash-prone work to a separate child process. A Python app could also choose to isolate work in another process: this compares these two configurations, not a guarantee for every request.

After a 4 s countdown, both stacks receive the crash concurrently. Counts cover the {{ (live.settings.rooms - 1) * live.settings.clients }} users outside Room 1 during the next 10 s, followed by 5 s for recovery. The view selects an affected user when there is one and shows the matching user on both sides. Disconnect counts remain after reconnection.

Both sides send the same scripted messages at the same rate. “Confirmed” means the server acknowledged a send, not that another user read it. Connections retry without replay; an unconfirmed send might have reached the server.

Worker assignment and this machine affect the result. Zero disconnects does not mean zero latency impact. A lost crash request alone does not prove a process died. Results describe the latest run, not throughput. Keep this demo local.
