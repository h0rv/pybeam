Where your Python actually runs

Contributor lab: compare one CPU-bound function across Python execution strategies and raw runtime modes on this machine. These probes are not application benchmarks.

One call, end to end

  1. BEAM process
    caller identity and mailbox
  2. mailbox
    queued, bounded by your limits
  3. Python context
    one OS thread it owns
  4. interpreter
    shared, own, or in a child process
  5. GIL
    enabled on conventional Python; check live state on free-threaded builds
  6. result as a message
    or a crash signal to the supervisor

A BEAM process is not a Python interpreter. A million of them waiting on Python share a fixed set of contexts, the same way a million web requests share a thread pool. The mode only decides what a context is:

This lab drives erlang-python contexts directly. PyBEAM tasks support WORKER and ISOLATED; own-GIL subinterpreters are unsupported because common native extensions cannot load in them. Raw isolated contexts in this lab can restart their child; PyBEAM isolated tasks never restart or retry after a child crash. Free-threaded Python is a build choice, not an ExecutionMode setting.

Read the numbers honestly

  • Everything runs on one shared {{ cores }}-core VM. "Separate nodes" are extra BEAM VMs on the same host, so they show the start and memory cost of a node, not a network.
  • The prefork pool is ProcessPoolExecutor, the model behind Celery's default worker, without a broker. When one of its workers dies the whole pool is marked broken.
  • The jobs in this lab are not persisted. Actor supervision restores fresh actors, not in-flight work. Durable tasks are a separate API and are not measured here.
  • One asyncio loop runs Python code on one thread and cannot preempt a coroutine that never yields. Both asyncio callers and runtime workers still consume memory; compare the live measurements rather than assuming equal costs.
