Where your Python actually runs

One CPU-bound function, run live on this machine the way Python does it today and in each PyBeam execution mode. You choose the mode; each one buys something and costs something.

One call, end to end

  1. BEAM process
    ≈2.7 KB, preemptively scheduled, millions per box
  2. mailbox
    queued, bounded by your limits
  3. Python context
    one OS thread it owns
  4. interpreter
    shared, own, or in a child process
  5. GIL
    held on 3.14, absent on 3.14t
  6. result as a message
    or a crash signal to the supervisor

A BEAM process is not a Python interpreter. A million of them waiting on Python share a fixed set of contexts, the same way a million web requests share a thread pool. The mode only decides what a context is:

ExecutionMode.WORKER · 3.14a thread in the one interpreter, sharing its GIL~1 ms start, ~15 KiB each, ~20 µs calls; every C extension worksCPU work runs one at a time; a segfault takes down the whole VM
ExecutionMode.WORKER · 3.14ta thread in the one interpreter, no GILthe same cheap threads, now in parallel on every coreneeds the free-threaded build and extensions that support it; still one crash domain
ExecutionMode.OWNGILa subinterpreter with its own GIL, same OS processparallel CPU on conventional 3.14; separate module state~80 ms and ~10 MiB each; NumPy, pydantic_core and other single-phase extensions refuse to load; still one crash domain
ExecutionMode.ISOLATEDa child OS process with its own interpreterparallel CPU and a crash kills only that child, which restarts~90 ms and ~24 MiB each; calls cost ~3× more because arguments cross a socket
separate nodesanother BEAM VM, here or on another machinescale past one box; whole-VM failure isolationa VM's start time and memory per node; network latency; you run more machines

Free-threaded or not is the interpreter you install (CPython 3.14 vs 3.14t), not a PyBeam option. The ExecutionMode setting is landing in pybeam#16: tasks accept WORKER today, OWNGIL and ISOLATED raise CapabilityUnavailable until erlang-python accepts a per-task mode. This lab drives erlang-python contexts directly so every mode can be measured now.

Read the numbers honestly

  • Everything runs on one shared {{ cores }}-core VM. "Separate nodes" are extra BEAM VMs on the same host, so they show the start and memory cost of a node, not a network.
  • The prefork pool is ProcessPoolExecutor, the model behind Celery's default worker, without a broker. When one of its workers dies the whole pool is marked broken.
  • Supervision restarts code, not work: PyBeam jobs are not persisted, so a job running in a crashed worker is lost unless your app retries it.
  • asyncio is just as cheap as BEAM processes for waiting callers. What it cannot do is run CPU work in parallel, preempt a coroutine that never yields, or survive a crash in one of them.
